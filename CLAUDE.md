## 16. GITHUB WORKFLOW

Never edit `main` directly unless Khanim explicitly requests it.

Default workflow:

1. Read the request.
2. Inspect relevant existing files.
3. Understand the current design system before editing.
4. Create/work on a Claude branch.
5. Make the smallest necessary changes.
6. Test the result.
7. Check desktop/mobile behavior when relevant.
8. Run path/link checks when relevant.
9. Review your own visual and technical work.
10. Commit.
11. Push the Claude branch.
12. Open a Pull Request into `main`.
13. STOP.

Do NOT merge into `main` automatically.

Khanim reviews and merges the Pull Request.

---

## 17. SELF-REVIEW

Before presenting any completed design change, ask yourself:

- Does this look intentionally designed?
- Does it strengthen the portfolio?
- Does it feel senior-level?
- Does it communicate the idea faster?
- Is hierarchy obvious?
- Is anything visually unnecessary?
- Does it still feel like Khanim’s portfolio?
- Would the work itself be more impressive without this UI treatment?

If the result feels generic, template-like, cluttered or visually weak:

**REDESIGN IT BEFORE PRESENTING IT.**

Do not wait for Khanim to identify obvious design problems.

---

## 18. MOST IMPORTANT RULE

Do not confuse “more design” with “better design.”

Every visual decision must have a reason.

Protect the quality of the existing portfolio while making each new project feel distinctive, memorable and professionally art-directed.
